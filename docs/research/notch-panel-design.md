# Notch panel design: proposals checked against primary sources

Research date: 2026-11-09. Machine: MacBook Pro (Mac15,6), macOS 27.0.1. Apple HIG pages were read from the JSON that backs each page (`developer.apple.com/tutorials/data/design/human-interface-guidelines/<page>.json`), so quotes match the live page on that date. Open-source code was read at the commits linked below. boring.notch is GPL-3.0: it is only described here, and no code was copied.

## Summary

| # | Proposal | Verdict | Recommended value |
|---|---|---|---|
| 1 | Two sizes (13, 11), two weights (regular, medium), no semibold; monospaced digits; SF Pro default design | **Adjust** | Sizes 13 and 11 match macOS Body and Subheadline. Weights regular and medium are fine, but Apple publishes nothing saying light text on dark looks heavier; the one Apple source on the topic goes heavier on dark. Pick the title weight by eye on the device. Agree on `.monospacedDigit()` and the default design. |
| 2 | Text 1.0 / 0.6 / 0.45; fills 0.06 / 0.10 / 0.16; step up with Increase Contrast | **Adjust** | 0.45 fails WCAG AA (4.41:1 on black, 4.18:1 on the 0.16 fill). Use **1.0 / 0.6 / 0.5**, or keep 0.45 only for disabled text. Fills are fine for hover and surfaces, but a 0.16 fill alone fails WCAG 1.4.11 as the keyboard-selection indicator: use the accent color (`selectedContentBackgroundColor`) for keyboard selection. Read `colorSchemeContrast`. |
| 3 | 4pt grid, one 12pt inset, concentric radii | **Agree** (4pt grid is house style; Apple doesn't publish it) | Inset 12. Bottom radius 20, so anything touching the bottom corners gets 20 − 12 = **8**. Compute radii by hand: `ConcentricRectangle` needs macOS 26. |
| 4 | Header beside the notch; clearance from `safeAreaInsets.top` | **Agree** | Header band height = `safeAreaInsets.top` (32 pt on this Mac), with text vertically centred in it. Search button 28×28 pt. Fall back to the menu bar height on screens without a notch. |
| 5 | Same width for list and search | **Agree** | One width, about **400** (inference: it leaves about 95 pt on each side of a 185 pt notch for the header after the 12 pt inset). Change only the height. |
| 6 | Snippet around the match, with the matched words highlighted | **Agree** | Highlight with weight (or weight plus color), not color alone. Maccy highlights in bold by default. |
| 7 | Custom template image for the menu bar icon | **Disagree** (optional) | The HIG explicitly allows an SF Symbol as-is. Keep `tray.and.arrow.down`, or make a *custom SF Symbol* if the brand needs one. |
| 8 | Keyboard-first: global search shortcut, ↑/↓, Return copies and closes, ⌘Return pastes, honour Concealed/Transient | **Adjust** | Return copies and closes (Maccy default). Use **⌥Return** for paste, not ⌘Return (⌘Return means *copy* in Raycast). Make paste opt-in, because it needs Accessibility permission, which the SPEC currently avoids. Concealed: hide the preview and refuse to save. Transient: hide and refuse. Also handle AutoGeneratedType and the legacy markers. |

### Findings that contradict the proposals

- **0.45 opacity fails WCAG AA** for 11 pt and 13 pt text (4.41:1 on black; needs 4.5:1).
- **No Apple source says light text on dark looks heavier.** WWDC23 "Design for spatial user interfaces" goes the other way: on visionOS's dark glass, body text moves from regular to *medium* and titles from semibold to *bold* "to improve the contrast of text". The HIG's emphasized weight for macOS Body is semibold.
- **A fill-only selection (0.16 on 0.10) is 1.2:1.** WCAG 1.4.11 requires 3:1 for "visual information required to identify … states".
- **`ConcentricRectangle` and the new `containerShape(_:)` are macOS 26+**, so they can't be used on the macOS 14 target.
- **The HIG says to consider an SF Symbol for menu bar extras.** A custom template image isn't required.
- **⌘Return conflicts with Raycast**, where it means "Copy to Clipboard". Maccy uses ⌥Return to paste.
- **Pasting into the previous app needs Accessibility permission** (Maccy, Paste). The SPEC's NotchPanelController notes deliberately avoid it.

## 1. Typography

### Findings

- **Default and minimum sizes.** The macOS default text size is 13 pt and the minimum is 10 pt. [HIG Typography](https://developer.apple.com/design/human-interface-guidelines/typography), [HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)
- **macOS built-in text styles**, from the [HIG Typography spec table](https://developer.apple.com/design/human-interface-guidelines/typography#macOS-built-in-text-styles):

  | Style | Weight | Size | Line height | Emphasized weight |
  |---|---|---|---|---|
  | Large Title | Regular | 26 | 32 | Bold |
  | Title 1 | Regular | 22 | 26 | Bold |
  | Title 2 | Regular | 17 | 22 | Bold |
  | Title 3 | Regular | 15 | 20 | Semibold |
  | Headline | Bold | 13 | 16 | Heavy |
  | Body | Regular | 13 | 16 | Semibold |
  | Callout | Regular | 12 | 15 | Semibold |
  | Subheadline | Regular | 11 | 14 | Semibold |
  | Footnote | Regular | 10 | 13 | Semibold |
  | Caption 1 | Regular | 10 | 13 | Medium |
  | Caption 2 | Medium | 10 | 13 | Semibold |

  Checked at runtime with `NSFont.preferredFont(forTextStyle:)` on macOS 27.0.1: the sizes match. Headline resolves to `.SFNS-Bold` and Caption 2 to `.SFNS-Medium`. macOS has no Dynamic Type ([HIG Typography, macOS](https://developer.apple.com/design/human-interface-guidelines/typography#macOS)).
- **Weight.** The HIG says: "avoid light font weights … prefer Regular, Medium, Semibold, or Bold" ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). It says nothing about weight for light text on dark backgrounds. The only Apple statement found is about visionOS glass: "font weight has been modified to be slightly heavier … regular weight for the body … On this platform, we use medium. And for titles, instead of semibold, we use bold" ([WWDC23 10076](https://developer.apple.com/videos/play/wwdc2023/10076/)). WWDC25 says system typography is "now bolder and left-aligned" ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/)). The [Dark Mode HIG](https://developer.apple.com/design/human-interface-guidelines/dark-mode) covers colors and vibrancy, not weight.
- **Optical sizes.** SF Text was designed for sizes below 20 pt and SF Display for 20 pt and above. Since SF Pro became a variable font, "there is no hard break around 20 points anymore and the design now transitions from Text to Display between 17 and 28 points", and "in code, this behavior is entirely automatic" ([WWDC20 10175](https://developer.apple.com/videos/play/wwdc2020/10175/)). The HIG says system fonts use "dynamic optical sizes" ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). Every Topstash size is ≤ 26, so the panel's text is all in the Text optical size.
- **Tracking.** "In a running app, the system font dynamically adjusts tracking at every point size", and manual tracking is only for mockups ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). The [macOS tracking table](https://developer.apple.com/design/human-interface-guidelines/typography#macOS-tracking-values) gives 11 pt: +6/1000 em (+0.06 pt), 12 pt: 0, 13 pt: −6/1000 em (−0.08 pt).
- **Monospaced digits.** `Font.monospacedDigit()` (macOS 10.15+) and `View.monospacedDigit()` (macOS 12+) give "fixed-width digits … also known as 'tabular figures'" ([Font](https://developer.apple.com/documentation/swiftui/font/monospaceddigit()), [View](https://developer.apple.com/documentation/swiftui/view/monospaceddigit())).
- **Leading.** For list rows "decreasing the space between lines (tight leading) can help the text fit", but avoid it for three or more lines ([Typography](https://developer.apple.com/design/human-interface-guidelines/typography)). Tight leading removes 2 pt on macOS ([WWDC20 10175](https://developer.apple.com/videos/play/wwdc2020/10175/)).

### Recommendation for Topstash

Use 13 pt (Body) and 11 pt (Subheadline), the system's own pair. Don't add tracking. Drop semibold if it looks heavy on the device, but record that as a judgment by eye, not an Apple rule. Medium for titles and Regular for the rest is a sound pair. For an Apple-text-style equivalent, Body's emphasized weight is Semibold. Use `.monospacedDigit()` on counts. Keep the default design; the HIG doesn't ask for rounded. Icons can follow the text size with `.imageScale` instead of fixed 18/26 pt (inference).

## 2. Color and contrast

### Findings

**WCAG math.** [WCAG 2.2](https://www.w3.org/TR/WCAG22/#dfn-relative-luminance) defines L = 0.2126R + 0.7152G + 0.0722B, with each channel c linearised as c/12.92 if c ≤ 0.04045, else ((c+0.055)/1.055)^2.4. [Contrast ratio](https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio) = (L1+0.05)/(L2+0.05). White at alpha a over #000 composites to grey a (this assumes source-over blending in gamma-encoded sRGB). Black has L = 0, so the ratio = (lin(a)+0.05)/0.05. For example, a = 0.45 gives lin = ((0.45+0.055)/1.055)^2.4 = 0.1706, so the ratio = 0.2206/0.05 = **4.41**.

| White alpha on #000 | Grey | L | Ratio | AA text (4.5:1)? |
|---|---|---|---|---|
| 1.0 | #FFFFFF | 1.0000 | 21.00 | yes |
| 0.85 | #D9D9D9 | 0.6921 | 14.84 | yes |
| 0.75 | #BFBFBF | 0.5225 | 11.45 | yes |
| 0.6 | #999999 | 0.3185 | 7.37 | yes (also AAA 7:1) |
| 0.55 | #8C8C8C | 0.2622 | 6.27 | yes |
| 0.5 | #808080 | 0.2140 | 5.28 | yes |
| **0.45** | #737373 | 0.1706 | **4.41** | **no** |
| 0.35 | #595959 | 0.1005 | 3.01 | no |

Text on a fill (the fill composited first, then the text):

| Fill | Text 1.0 | Text 0.6 | Text 0.5 | Text 0.45 |
|---|---|---|---|---|
| 0.06 (hover) | 19.13 | 7.24 | 5.33 | 4.53 |
| 0.10 (surface) | 17.49 | 6.95 | 5.22 | **4.48** |
| 0.16 (selected) | 14.59 | 6.23 | 4.80 | **4.18** |

Fills against black: 0.06 → 1.10, 0.10 → 1.20, 0.16 → 1.44. From 0.10 to 0.16 → 1.20. A fill needs alpha ≈ 0.35 to reach 3:1 against black. The system accent `selectedContentBackgroundColor` (#0059D1 at runtime, default blue) is 3.35:1 against black. White text on it is 6.27:1, and white 0.85 text on it is 4.96:1.

- **Requirements.** [WCAG 1.4.3](https://www.w3.org/TR/WCAG22/#contrast-minimum) asks for 4.5:1, or 3:1 for large text (≥ 18 pt, or 14 pt bold). Text in an *inactive* component is exempt. [1.4.11](https://www.w3.org/TR/WCAG22/#non-text-contrast) asks for 3:1 for the "visual information required to identify user interface components and states". The HIG's table applies AA (4.5:1 up to 17 pt) and adds: "If your app doesn't provide this minimum contrast by default, ensure it at least provides a higher contrast color scheme when the system setting Increase Contrast is turned on" ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Dark Mode HIG: "at a minimum … no lower than 4.5:1 … strive for a contrast ratio of 7:1, especially in small text" ([Dark Mode](https://developer.apple.com/design/human-interface-guidelines/dark-mode)).
- **Apple's values aren't published.** The [HIG Color macOS table](https://developer.apple.com/design/human-interface-guidelines/color#macOS) lists labelColor, secondaryLabelColor, tertiaryLabelColor and quaternaryLabelColor by purpose, with no values. The HIG says not to hard-code them: "actual color values may fluctuate from release to release". I read them at runtime with a scratch Swift script (`NSAppearance(named: .darkAqua).performAsCurrentDrawingAppearance`, then `usingColorSpace(.sRGB)`) on macOS 27.0.1:

  | Color (darkAqua) | Value | Ratio on #000 |
  |---|---|---|
  | labelColor | white α 0.847 | 14.73 |
  | secondaryLabelColor | white α 0.549 | 6.24 |
  | tertiaryLabelColor | white α 0.247 | 1.99 |
  | quaternaryLabelColor | white α 0.098 | — |
  | systemFill ([macOS 14+](https://developer.apple.com/documentation/appkit/nscolor/systemfill)) | white α 0.098 | |
  | secondarySystemFill | white α 0.078 | |
  | tertiarySystemFill | white α 0.047 | |
  | quaternarySystemFill | white α 0.027 | |
  | quinarySystemFill | white α 0.008 | |
  | selectedContentBackgroundColor | #0059D1 (0, 0.349, 0.820) | 3.35 |
  | unemphasizedSelectedContentBackgroundColor | #464646 (0.275) | 2.23 |

  I couldn't read the Increase Contrast variants. Resolving under `.accessibilityHighContrastDarkAqua` returned the same values, and Apple's docs say not to assign that appearance directly: "AppKit then returns this type when the user enables the Increase Contrast option" ([doc](https://developer.apple.com/documentation/appkit/nsappearance/name-swift.struct/accessibilityhighcontrastdarkaqua)). Increase Contrast was off on this machine.
- **Detecting Increase Contrast.** In SwiftUI, read `@Environment(\.colorSchemeContrast)`, which is `.standard` or `.increased`, on macOS 10.15+. SwiftUI redraws when it changes ([colorSchemeContrast](https://developer.apple.com/documentation/swiftui/environmentvalues/colorschemecontrast), [ColorSchemeContrast](https://developer.apple.com/documentation/swiftui/colorschemecontrast)). In AppKit, read `NSWorkspace.shared.accessibilityDisplayShouldIncreaseContrast` and listen for `accessibilityDisplayOptionsDidChangeNotification` ([doc](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldincreasecontrast)). The HIG asks custom colors for "an increased contrast option for each variant that provides a significantly higher amount of visual differentiation" ([Color](https://developer.apple.com/design/human-interface-guidelines/color)).

### Recommendation for Topstash

Text: **1.0 / 0.6 / 0.5**. 0.5 still passes on the 0.16 fill (4.80:1). Keep 0.45 or lower only for the disabled "Nothing to save" state, which WCAG exempts. Fills: hover 0.06, surface 0.10 (≈ systemFill 0.098), pressed or mouse-selected 0.16. For **keyboard selection**, use `Color(nsColor: .selectedContentBackgroundColor)`, with text at 1.0 and previews at 0.85, so the state reaches 3:1. Maccy does the same with `accentColor.opacity(0.8)`. With Increase Contrast, use for example 1.0 / 0.8 / 0.65 and fills 0.12 / 0.20 / 0.28. These are inference: no Apple numbers exist for a custom black surface. Check that the environment value reaches SwiftUI inside the `NSPanel`'s hosting view by testing on the device.

## 3. Layout, spacing and concentric radii

### Findings

- **No macOS spacing grid is published.** The [HIG Layout page](https://developer.apple.com/design/human-interface-guidelines/layout) has no 4 pt or 8 pt grid for macOS. Its macOS section says only: "Avoid placing controls or critical information at the bottom of a window" and "Avoid displaying content behind the camera housing". The general guidance: "Align elements to make them easier to scan" and "Group related items … using negative space, container shapes, or separator lines". The HIG's spacing number: "about 12 points of padding around elements that include a bezel … about 24 points … without a bezel". Its control sizes: macOS default control 28×28 pt, minimum 20×20 pt ([Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). Apple's own metrics aren't on a 4 pt grid (line heights 13, 15; the status bar is 22 at runtime). So a 4 pt grid is house style.
- **Concentricity (WWDC25).** "By aligning radii and margins around a shared center, shapes can comfortably nest within each other … fixed shapes have a constant corner radius. Capsules use a radius that's half the height of the container. And concentric shapes calculate their radius by subtracting padding from the parent's." Also: "use a concentric shape with a fallback radius" ([WWDC25 356](https://developer.apple.com/videos/play/wwdc2025/356/)).
- **API availability.** [`ConcentricRectangle`](https://developer.apple.com/documentation/swiftui/concentricrectangle) and [`containerShape(_: some RoundedRectangularShape)`](https://developer.apple.com/documentation/swiftui/view/containershape(_:)) are **macOS 26.0+**. The docs note that a corner far from the container's corner may resolve to 0, and suggest `concentric(minimum:)` for that case. The older [`ContainerRelativeShape`](https://developer.apple.com/documentation/swiftui/containerrelativeshape) (macOS 11+) together with [`containerShape<T: InsettableShape>(_:)`](https://developer.apple.com/documentation/swiftui/view/containershape(_:)-qn9q) (macOS 12+) is available on macOS 14. It needs an insettable container, which the custom notch shape (with outward top corners) probably isn't (inference). [`RectangleCornerRadii`](https://developer.apple.com/documentation/swiftui/rectanglecornerradii) (macOS 13+) allows uneven corners.
- **Live Activities HIG.** "Use even, matching margins between rounded shapes and the edges … use ContainerRelativeShape to match the corner radius … instead of hard-coding" ([Live Activities](https://developer.apple.com/design/human-interface-guidelines/live-activities)).
- **Prior art.** Maccy's comment reads: "Radius used for items inset by the padding. Ensures they visually have the same curvature as the menu." It uses 7 pt on macOS 26 and 4 pt before ([Popup.swift#L26-L32](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/Observables/Popup.swift#L26-L32)). NotchDrop pairs an outer radius of 32 with 16 pt padding and 16 pt inner radii, which is concentric ([NotchView.swift#L35-L40](https://github.com/Lakr233/NotchDrop/blob/e70b3d715a99e47de6eb823540282eafc7401a3a/NotchDrop/NotchView.swift#L35-L40), [NotchViewModel.swift#L70-L71](https://github.com/Lakr233/NotchDrop/blob/e70b3d715a99e47de6eb823540282eafc7401a3a/NotchDrop/NotchViewModel.swift#L70-L71)).

### Recommendation for Topstash

Use a 12 pt outer inset for every surface: the card, the rows and the field. With a bottom radius of 20, rows and the field get 20 − 12 = **8 pt**, which matches today's row radius. The card sits far from any convex corner, because the top corners curve outward, so concentricity doesn't constrain it. Use the same 8 pt fixed radius for a single radius family (inference). "Every text edge aligns" should mean text sits at inset + inner padding, for example 12 + 8 = 20, for the header title, the card text, row titles and the field text. The surfaces themselves align at 12. Compute radii as `outer − inset` constants, because `ConcentricRectangle` isn't available on macOS 14.

## 4. Dynamic Island, and how notch apps lay out content

### Findings: Apple

- **Presentations.** Compact is "two separate elements: one on the leading side of the TrueDepth camera and one on the trailing side". Minimal is used when several activities are running. Expanded appears on touch and hold ([Live Activities](https://developer.apple.com/design/human-interface-guidelines/live-activities)).
- **Space beside the sensor.** Compact: "Keep content as narrow as possible and ensure it's snug against the TrueDepth camera … don't add padding between content and the TrueDepth camera", and "design them to read as a single piece of information". Expanded: "Wrap content tightly around the TrueDepth camera … avoid leaving too much room around it". "Maintain the relative placement of elements … Ensure information and layouts expand predictably."
- **Margins and height.** "The standard layout margin for Live Activities on the Lock Screen is 14 points." "Keep content compact and snug within a margin that's concentric to the outer edge." "Don't draw content all the way to the edge of the Dynamic Island." "Dynamically change the height … reduce the height … to only use the space needed."
- **Background.** "Live Activities in the Dynamic Island use a black opaque background", and custom backgrounds aren't allowed there. In dark mode "a key line appears around the Dynamic Island".
- **Sizes (iPhone).** Expanded is 408 × 84–160 (430-pt-wide phone) or 371 × 84–160. Compact is 62.33 × 36.67 per side. For macOS the HIG says "Use the provided iOS dimensions." `DynamicIslandExpandedRegionPosition` now lists macOS 27.3 (beta) ([doc](https://developer.apple.com/documentation/widgetkit/dynamicislandexpandedregionposition)).
- **This Mac's notch**, read at runtime: `safeAreaInsets.top` = 32. The `auxiliaryTopLeftArea` and right areas are 663.5 pt each on a 1512 pt screen, so the notch is 185 pt wide. [`safeAreaInsets`](https://developer.apple.com/documentation/appkit/nsscreen/safeareainsets) (macOS 12+): "the insets reflect the portion of the screen covered by the camera housing". The current fixed clearance of 38 pt equals 32 + 6.

Make the header band exactly `screen.safeAreaInsets.top` tall, and vertically centre the title, count and search button in it. On screens without a notch, `safeAreaInsets.top` is 0, so use the menu bar height. The SPEC hides the shape there, so the band can stay at that height (inference). The search button should be at least 28×28 pt, the HIG default macOS control size; 32 pt leaves room. Moving "Show all" to the top also follows the HIG's macOS advice against controls at the bottom. Let the panel's height follow its content, as the HIG asks for Live Activities.

## 5. Menu bar extra

### Findings

- "Consider using a symbol to represent your menu bar extra. You can create an interface icon or you can choose one of the SF Symbols, using it as-is or customizing it … Both … use black and clear colors … The menu bar's height is 24 pt." ([The menu bar](https://developer.apple.com/design/human-interface-guidelines/the-menu-bar#Menu-bar-extras))
- "Display a menu — not a popover — when people click your menu bar extra." Topstash's `MenuBarExtra` uses the default menu style, which complies.
- Template images "should consist of only black and clear colors", and alpha may vary ([NSImage.isTemplate](https://developer.apple.com/documentation/appkit/nsimage/istemplate)). [Images HIG](https://developer.apple.com/design/human-interface-guidelines/images): "transparency is necessary in … menu icons … that serve as template images". For custom symbols, the HIG says to export a similar symbol's template and match its optical weight ([SF Symbols](https://developer.apple.com/design/human-interface-guidelines/sf-symbols)).
- `MenuBarExtra` is macOS 13+. "An app that only shows in the menu bar will be automatically terminated if the user removes the extra" ([MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra)).
- Apple publishes no pixel size for menu bar extra icons; the HIG gives only the 24 pt bar height. At runtime `NSStatusBar.system.thickness` = 22 on this notched Mac.

### Recommendation for Topstash

Keep the SF Symbol. It's the HIG's first suggestion and gets weight, scale and appearance handling for free. If a brand mark is needed, make a custom SF Symbol from an exported template rather than a bitmap template image.

## 6. Keyboard-first retrieval and clipboard markers

### Findings

| App | Return | Modifier variants | Other |
|---|---|---|---|
| Spotlight ([shortcuts](https://support.apple.com/guide/mac-help/spotlight-keyboard-shortcuts-mh26783/mac)) | Open a result | ⌘R reveals the item in Finder; ⌘4 searches the Clipboard | Spotlight's metrics (field size, row height) aren't published |
| Raycast ([Clipboard History](https://manual.raycast.com/clipboard-history)) | Primary action: "Paste to Active App" by default (configurable) | ⌘↵ = Copy to Clipboard | Passwords and Keychain Access are excluded by default |
| Alfred ([Clipboard](https://www.alfredapp.com/help/features/clipboard/)) | "Pasting on Return is active by default" | — | "By default, Alfred ignores clipboard data marked as Concealed" |
| Paste ([shortcuts](https://pasteapp.io/help/keyboard-shortcuts), [Paste on Mac](https://pasteapp.io/help/paste-on-mac)) | Paste selected items | ⇧Return = plain text; ⌘C = copy; Esc = dismiss | Without Accessibility permission, Return copies instead |
| Maccy ([README](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/README.md)) | Copy and close the popup; paste only if "Paste automatically" is on ([History.swift#L349-L380](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/Observables/History.swift#L349-L380)) | ⌥↵ = paste; ⌥⇧↵ = paste without formatting; Esc = close ([KeyChord.swift#L121](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/KeyChord.swift#L121)) | Row height 24 pt on macOS 26 (22 before), selection radius 7, search field 23 pt tall, default window 450 × 800, matches highlighted in **bold** by default |

- **Pasting needs Accessibility permission.** Maccy posts a synthetic ⌘V with `CGEvent` after `Accessibility.check()` ([Clipboard.swift](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/Clipboard.swift)). Its README tells users to add Maccy under Privacy & Security → Accessibility. Apple's preflight API for posting events is [`CGPreflightPostEventAccess()`](https://developer.apple.com/documentation/coregraphics/cgpreflightposteventaccess()) (macOS 10.15+).
- **HIG keyboard guidance.** "Prefer the Command key as the main modifier … Use the Option modifier sparingly for less-common commands or power features" ([Keyboards](https://developer.apple.com/design/human-interface-guidelines/keyboards#Custom-keyboard-shortcuts)). ⌥⌘S isn't in the standard table. ⌥⌘F ("Jump to the search field control"), ⇧⌘V and ⇧⌘C are standard, so a global hotkey on them would take them from every app (inference). Search HIG: "start search immediately when a person types" and "consider immediately focusing the field" ([Search fields](https://developer.apple.com/design/human-interface-guidelines/search-fields)). [`onKeyPress`](https://developer.apple.com/documentation/swiftui/view/onkeypress(_:action:)) is macOS 14+ and needs focus.
- **nspasteboard.org** ([nspasteboard.org](http://nspasteboard.org/)):
  - `org.nspasteboard.TransientType`: "content will be on the pasteboard only momentarily … should not be recorded or displayed in a pasteboard history."
  - `org.nspasteboard.ConcealedType`: "should be treated as confidential. If displayed on screen it should be visually obfuscated. Avoid recording it to a file, or consider encrypting it."
  - `org.nspasteboard.AutoGeneratedType`: "the user had no intention to Copy this content … probably should not be recorded … but (if not also marked transient) might need to be displayed as the 'current' pasteboard content."
  - Clipboard historians should also support the legacy markers `de.petermaurer.TransientPasteboardType`, `com.typeit4me.clipping`, `Pasteboard generator type` and `com.agilebits.onepassword`.
  - Maccy never stores anything carrying the three universal types, and by default also ignores the four legacy markers plus `net.antelle.keeweb` ([Clipboard.swift#L27-L31](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/Clipboard.swift#L27-L31), [Defaults.Keys+Names.swift#L39-L48](https://github.com/p0deje/Maccy/blob/f0b571e32e4031d7b91ba811f50d0f33e8e5548b/Maccy/Extensions/Defaults.Keys%2BNames.swift#L39-L48)).

### Recommendation for Topstash

- **Keys:** ↑/↓ move the selection, the field keeps focus, typing filters at once, Return copies and closes the panel, Esc closes it.
- **Paste:** make it opt-in, on **⌥Return**, and show the Accessibility prompt only when it's first used. This keeps the default app free of permissions, as the SPEC intends. Because `NotchPanel` doesn't activate the app, the previous app should still be frontmost when ⌘V is posted (inference; verify).
- **Global search shortcut:** leave it unset by default, or pick one outside the HIG standard table, and let users set it in Settings like ⌥⌘S.
- **Search rows:** show a snippet centred on the first match, with every query word in medium or semibold weight plus full white, so the highlight doesn't rely on color alone.
- **Concealed** (or `com.agilebits.onepassword`): show "Hidden content (password)" in place of the preview, and refuse to save.
- **Transient** (or a legacy transient marker): show nothing and refuse to save.
- **AutoGenerated:** show the preview with a hint, and allow an explicit save, because Topstash only saves on user action (inference).

## Open questions

- **Increase Contrast values** for label and fill colors: couldn't read them without turning the setting on, and Apple doesn't publish them. Turn on Increase Contrast and rerun the scratch script.
- **Notch height on other Macs:** only this Mac15,6 was measured (32 pt, 185 pt wide). Don't assume 32 elsewhere; always read `safeAreaInsets.top`.
- **Menu bar height:** the HIG says 24 pt, `NSStatusBar.thickness` returns 22, and the notch band is 32 pt here. It's unclear which applies to icon design on notched Macs.
- **Search field and row metrics for Spotlight, Raycast and Alfred:** none are published. Only Maccy's (open source) are known.
- **Spotlight's macOS 26/27 Clipboard view behavior** (what Return does there): I couldn't find the support page.
- **Clipboard privacy:** it's unconfirmed whether only reading `NSPasteboard.types` (to detect the markers) triggers macOS's paste-access alert. Test it, together with the existing clipboard privacy note in the SPEC.
- **Whether `colorSchemeContrast` updates inside the non-activating `NSPanel`'s hosting view:** expected but unverified.
